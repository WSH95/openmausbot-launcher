## Verdict

The recorded evidence is real and reproducible. The transcript hashes in
`docs/validation/2026-09-08-m1-hosts.json` match the files still under
`/tmp/oml-m1-hostcheck-VslL6s/logs` (6/6), the two recorded source-file
hashes match (2/2), the message epochs fall inside the recorded runtime-turn
windows, the T12 archive corroborates its run, and the external package's
SHA-256 is unchanged. The defects are in scope and bookkeeping, not in the
truthfulness of the record.

M1 is substantially, not fully, delivered against `docs/design.md`. One
specified verb is missing. Several design host checks had never been
evidenced; this pass ran them and they pass. Half of the "input relay"
acceptance item had never touched a real server; this pass ran it and it
works. Testing beyond the suite also produced six defects the 154 tests do
not reach. Four need a real process, sandbox, or port: the webhook port
collision, the sandbox hint that never fires, a blocked network reported as
an identity failure, and the `(undefined)` roster line. Two came out of the
scripted runs: the adopted project that can never dispatch, and the dropped
`carried` flag.

Two claims in the existing documents did not survive the test.
`docs/evidence.md:22-24` says `up` "names the sandbox cause in its hint"; on a
real sandboxed failure it does not (finding 24). `docs/evidence.md:62` says
Codex "ran `status` from inside its workspace-write sandbox"; it cannot —
`status` exits 3 there (finding 26).

## What this pass verified for the first time on real OpenMausBot

- `import --adopt` into a second project: `package: null`, identical lead and
  bot ids, `owned: false`, and `status` there returns `run: null`.
- `answer --deny` on a real approval card: outcome `rejected`; the lead quoted
  the tool's own `user rejected MCP tool call` back and finished.
- `answer --allow` on a real card: outcome `allowed-once` in both the MCP
  tool-approval and the peer-contact form. "Always allow" was never chosen.
- The peer-approval card that `approvePeerComms` gates: title
  "@Sudo wants to contact @Sage", options Allow / Deny / Always allow, and a
  per-peer `allowKey` of `ask_bot:<sage id>`.
- `interrupt` against a working bot: exit 0, `interrupted: true`, and the bot
  idle within one second.
- `report --md` closing a real run `passed`, and `report --run last` in both
  dry-run and re-report forms, the latter appending exactly one `reanalysis`
  entry and leaving the original result intact.
- A background `watch --max-seconds 570` returning at the next terminal state
  after **60 s**, concurrently with a foreground 100 s watch; both reported
  DONE and the state file's md5 changed, so both checkpointed.
- `up` from Grok Build and Codex CLI against the **real** server, with the
  server outliving the host process and `down` stopping it from another shell.
- The Codex `workspace-write` failure as a byte-level artifact: exit 1 with
  `syscall: 'listen'`, `code: 'EPERM'`, port 8905.
- Codex `read-only` listing `openmausbot-launcher` among its skills without
  running a command, and Codex `workspace-write` writing the state file.
- The Claude trigger phrase "run T10 through the team" loading the
  `openmausbot-launcher` skill as its first tool call.
- `${CLAUDE_SKILL_DIR}` resolving by load-time text substitution rather than
  an environment variable: the skill text arrives with the absolute path
  already written in, while `echo "${CLAUDE_SKILL_DIR:-unset}"` in the same
  session's shell prints `unset`.
- Provider keys and `OMB_TOKEN` absent from both server processes, proven from
  a single shell that had all three decoy keys set.
